### Zonit.Extensions

- **[medium]** Schedule calendar arithmetic freezes the UTC offset and brute-forces minute-by-minute for up to 4 years
  
  `Source/Zonit.Extensions/ValueObjects/Time/Schedule.cs:461-555`

  Two problems in `GetNextCalendarOccurrence`/`AdvanceToNextPotentialMatch`. (1) DST: the input is converted to the target zone once (line 464) and every subsequent candidate is rebuilt with `new DateTimeOffset(..., dt.Offset)` â€” the offset captured *before* the search. A "daily at 15:00 Europe/Warsaw" schedule computed in winter returns a moment that is 14:00 local after the March transition, and `MatchesCalendar` then compares those shifted components. The `timeZone` parameter therefore does not actually deliver zone-correct results across a DST boundary. (2) Cost: when `Second` is set, `AdvanceToNextPotentialMatch` steps one minute at a time; everything else falls through to `dt.AddSeconds(1)`. `Schedule.EveryYear(2, 29)` searches up to the 4-year `maxDate` â€” roughly 2.1 million `DateTimeOffset` constructions per call â€” and `EveryYear(12, 25)` up to ~525k. This runs on every scheduler tick. Fix: do the arithmetic in the zone's local wall-clock (`TimeZoneInfo.ConvertTime` per candidate, or DateTime+TimeZoneInfo instead of a frozen offset), and advance by the largest unconstrained unit (jump straight to the next matching month/day rather than iterating minutes).

- **[medium]** Color violates the Equals/GetHashCode contract â€” equal colours can hash differently
  
  `Source/Zonit.Extensions/ValueObjects/Files/Color.cs:524,534`

  `Equals` uses epsilon tolerances (`|Î”L| < 0.0001`, `|Î”H| < 0.01`) while `GetHashCode` combines `Math.Round(L, 4)`, `Math.Round(C, 4)`, `Math.Round(H, 2)`, `Math.Round(Alpha, 4)` â€” rounding is not a tolerance, so two values on opposite sides of a rounding boundary compare equal but hash differently. VERIFIED: `Color.FromOklch(0.123449, 0.1, 100)` and `Color.FromOklch(0.123451, 0.1, 100)` give `c1 == c2` â†’ True with `GetHashCode()` equal â†’ False. `Color` is therefore unsafe as a `Dictionary`/`HashSet` key and `Distinct()` over colours is non-deterministic. Fix: quantise in `Equals` the same way `GetHashCode` does (compare the rounded values), or drop the epsilon and compare exact doubles.

- **[medium]** Permission/Identity authorization fails OPEN for an empty permission
  
  `Source/Zonit.Extensions/ValueObjects/Auth/Permission.cs:101 and ValueObjects/Auth/Identity.cs:117`

  `Permission.Implies` returns true when `other` has no value ("empty permission is universally allowed") and `Identity.HasPermission` returns true up-front when the requested permission is empty â€” even for an identity with zero granted permissions. VERIFIED: an identity holding only `orders.read` returns True for `HasPermission("")`. Combined with `implicit operator Permission(string?)` mapping null/whitespace to `Empty`, any code path that reads a permission name from configuration, a route value or an attribute and gets back a blank string grants access instead of denying it. For a type whose stated job is driving `[RequirePermission]`, fail-open is the wrong default. Fix: return false for an empty requested permission (or throw), and make `[RequirePermission("")]` a hard error at registration.

- **[medium]** Price arithmetic silently breaks the non-negative invariant
  
  `Source/Zonit.Extensions/ValueObjects/Money/Price.cs:71,79,87,104,248,258,274`

  The public constructor rejects negatives, but `operator -`, `operator *`, `operator /`, `ApplyPercentage`, `CalculatePercentage` and `Negate` all construct via `new Price(..., allowNegative: true)`. `new Price(5m) - new Price(10m)` therefore yields a `Price` whose `Value` is -5, which then flows into EF columns, `Money.ToPrice()` comparisons and UI formatting. The entire reason `Price` exists separately from `Money` is this invariant. Fix: have subtraction/multiplication return `Money` (the signed type), or throw/clamp, or at minimum expose the current behaviour via an explicit `Price.SubtractUnchecked`.

- **[medium]** ValueObjectJsonConverterFactory is dead code and inconsistent with the types it claims to cover
  
  `Source/Zonit.Extensions/ValueObjects/ValueObjectJsonConverterFactory.cs:12-66`

  All 14 types listed in `CanConvert` already declare `[JsonConverter(typeof(TheSameConverter))]` on the type itself, and `CreateConverter` returns exactly those converters â€” so registering the factory in `JsonSerializerOptions.Converters` produces byte-identical output. Meanwhile it omits seven VOs that do have converters (`Permission`, `Role`, `Credential`, `Identity`, `Organization`, `Project`, `UrlPath`), and `UrlPathJsonConverter` is declared in this very file (line 129) yet never referenced by the factory. Its XML summary claims it "Automatically handles serialization/deserialization of all Zonit value objects". Either delete the factory (and the README setup step that recommends it) or make it the single source of truth by removing the per-type attributes.

- **[medium]** ValueObjectTypeConverter<T> does a reflective MethodInfo.Invoke plus an object[] allocation on every model bind
  
  `Source/Zonit.Extensions/Converters/ValueObjectTypeConverter.cs:53-58,75`

  `object?[] parameters = [stringValue, null]; var result = TryCreateMethod.Invoke(null, parameters);` runs for every `Title`, `Description`, `Content`, `UrlSlug`, `Url`, `UrlPath`, `Culture`, `TimeZone`, `Currency`, `Permission`, `Role` and `Credential` bound from a form field, route value, query string or IConfiguration key â€” i.e. several times per request in a Blazor/MVC app. Each call allocates the array, boxes the struct result, and `ConvertTo` adds a second `PropertyInfo.GetValue` box. The `[DynamicallyAccessedMembers]` annotation keeps it trim-clean (0 warnings confirmed) but forces PublicMethods|PublicProperties|PublicFields to be rooted for every instantiation, which is the opposite of what a trimmable package wants. It also throws `InvalidOperationException` at runtime â€” not compile time â€” for any VO missing `TryCreate`. Fix: replace the reflection with a `static abstract` interface member (`interface IValueObject<T> { static abstract bool TryCreate(string?, out T); }`, available since .NET 7) so the converter becomes `ValueObjectTypeConverter<T> where T : IValueObject<T>` with a direct call and a compile-time error for non-conforming types. Note `Currency.Value` (Currency.cs:64) exists purely as an alias for `Code` to satisfy this reflection â€” that hack disappears with the interface.

- **[medium]** Asset always computes MD5 alongside SHA256, even though MD5 is [Obsolete]
  
  `Source/Zonit.Extensions/ValueObjects/Files/Asset.cs:261-262,320-321`

  Every constructor runs both `SHA256.HashData(data)` and `MD5.HashData(data)` â€” two full passes over a payload that may be up to `MaxSize` (100 MB) â€” on the upload hot path, unconditionally. The `Md5` property is marked `[Obsolete(DiagnosticId = "ZONIT0001")]` and its own doc says "For any new code, use Sha256. This property may be removed in a future major version." Fix: compute MD5 lazily on first access to `Md5`/`VerifyMd5`/`ToStorageBytes`, or drop it and bump the storage version. Related: the V4 storage format reserves a fixed 24 bytes for it in every persisted blob (Asset.Storage.cs:49,86-90).

- **[medium]** Asset JSON output is culture-dependent
  
  `Source/Zonit.Extensions/ValueObjects/Files/Asset.Converters.cs:177`

  `writer.WriteString("size", value.Size.ToString())` calls `FileSize.FormatAuto`, which defaults to `CultureInfo.CurrentCulture` (FileSize.cs:305,318-325). The same document serialised on a pl-PL host emits `"size":"1,5 MB"` and on en-US `"size":"1.5 MB"`. JSON payloads must be culture-invariant. Related inconsistencies in `FileSize.ToString(string?, IFormatProvider?)`: the `"B"` branch (line 309) and the `< BytesPerKilobyte` branch of `FormatAuto` (line 320) use plain interpolation and silently ignore the supplied `formatProvider`, while the other branches honour it via `string.Create(formatProvider, ...)`. Fix: pass `CultureInfo.InvariantCulture` from the JSON writer and route every FileSize branch through the provider.

- **[medium]** Culture allocates a fresh CultureInfo on every property read and accepts ICU-synthesised tags
  
  `Source/Zonit.Extensions/ValueObjects/Localization/Culture.cs:71,94,99,105,110,115`

  `ToCultureInfo()` is `new CultureInfo(Value)` and `LanguageCode`, `NativeName`, `EnglishName` each call it â€” so reading all four properties allocates four `CultureInfo` objects, in a type designed to be read repeatedly inside localization loops. `CultureInfo.GetCultureInfo(name)` returns a cached instance and should be used instead (including in the constructor). Separately, validation is weak: VERIFIED that `Culture.TryCreate("xx-XX")` and `Culture.TryCreate("qqq")` both return true on .NET 10 with ICU, because ICU synthesises cultures for well-formed-looking tags. If the intent is "only real cultures", use `CultureInfo.GetCultureInfo(name, predefinedOnly: true)`.

- **[medium]** Url is a mutable struct with a lazily-written field â€” silent cache defeat plus a benign data race
  
  `Source/Zonit.Extensions/ValueObjects/Text/Url.cs:22,39,59`

  `Url` is deliberately non-`readonly` so `Uri => _uri ??= â€¦` can memoise. The consequence (acknowledged in the file's own comment) is that storing a `Url` in a `readonly` field, passing it by `in`, or holding it inside another `readonly struct` â€” which is exactly what a value-object-heavy codebase does â€” triggers a defensive copy on every property access, so the cache never survives and each `Scheme`/`Host`/`Path` read re-parses the URI. It also means `Url` cannot be a field of any other Zonit VO without the same silent penalty, and two threads reading a shared instance race on `_uri` (harmless in outcome, but it is a mutation of shared state in a type documented as a value object). Fix: make it `readonly` and cache nothing (Uri parsing is cheap), or move the cache to a class-typed holder, or eagerly parse in the constructor into readonly fields for the handful of components actually exposed.

- **[medium]** Description recomputes its grapheme length on every access and re-validates in TryCreate â€” the exact costs Title was fixed for
  
  `Source/Zonit.Extensions/ValueObjects/Text/Description.cs:61,192`

  `Title` caches `_length` in the constructor with an explicit comment that this avoids a fresh `new StringInfo(_value)` walk per `Length` read, and adds a private trusted-input ctor so `TryCreate` does not re-normalise (Title.cs:50,101,213). `Description` â€” the sibling type with the identical shape and a 160-char limit, i.e. the one more likely to be long â€” got neither: `Length` allocates a `StringInfo` on every call (used by UI counters and validators), and `TryCreate` normalises + counts graphemes and then calls the public ctor which normalises + counts again. Apply the Title treatment to Description; the two files should be structurally identical.

- **[medium]** Asset.MimeType.Type/Subtype allocate a string[] per access, multiplying through Category and the Is* checks
  
  `Source/Zonit.Extensions/ValueObjects/Files/Asset.MimeType.cs:95,102`

  `Type => _value.Split('/')[0]` and `Subtype => _value.Split('/')[1].Split(';')[0].Trim()` allocate a new array (and substrings) on every read. `IsImage`/`IsVideo`/`IsAudio`/`IsText` each call `Type`, and `Asset.Category` (Asset.cs:185) switches on `MediaType.Type` and then evaluates `IsDocument`/`IsArchive` â€” so rendering a file list allocates several arrays per row. Fix: `_value.AsSpan(0, _value.IndexOf('/'))` with `MemoryExtensions.Equals(..., OrdinalIgnoreCase)`, or precompute Type/Subtype in the constructor. `Permission.Tokens` (Permission.cs:49) has the same `Value.Split('.')` per-access allocation, though `Implies` correctly avoids it.

- **[medium]** BaseException cannot carry an inner exception and re-reflects twice per instance
  
  `Source/Zonit.Extensions/Exceptions/BaseException.cs:35,90,100`

  Neither `BaseException(string, string, params object[])` nor `BaseException<TErrorCode>(TErrorCode, params object[])` accepts an `Exception innerException`, and there is no protected overload â€” so a handler that catches a low-level failure and rethrows a domain exception permanently loses the cause; `ex.InnerException` is always null and stack traces are truncated at the boundary. Separately, `GetErrorKey` and `GetTemplate` each independently run `code.GetType().GetField(code.ToString())` + `GetCustomAttribute<DisplayAttribute>()`, so every instance pays two field lookups, two attribute materialisations and two `ToString()` allocations, uncached. Also note this reflection is only unverifiable-by-analyser rather than provably safe: `Type.GetField` on the result of `GetType()` over an unannotated `TErrorCode` relies on the trimmer preserving enum fields and their `[Display]` attributes; under aggressive attribute trimming the messages silently degrade to `code.ToString()`. Fix: add inner-exception overloads and cache `(enum value) â†’ (key, template)` in a static `Dictionary` or a frozen lookup.

- **[medium]** AssemblyProvider swallows load failures in Release and carries a dead trim suppression
  
  `Source/Zonit.Extensions/Reflection/AssemblyProvider.cs:58,70,77`

Fix: accept an optional `ILogger`/`Action<string>` (or use `Trace`/EventSource) and delete the redundant suppression.

### Zonit.Extensions.Auth

- **[medium]** Initialize() silently swallows a snapshot change because Identity equality is Id-only
  
  `Source/Zonit.Extensions.Auth/Repositories/AuthenticatedRepository.cs:15`

  `var changed = !_current.Equals(identity);` â€” `Identity.Equals` compares `_id` ONLY (Identity.cs:129). So re-initializing the same user with a different snapshot (Id-only -> hydrated, or a role/permission grant applied mid-circuit) mutates `_current` but does not raise `OnChange`. Downstream, `Zonit.Extensions.Website.Authentication.SessionAuthenticationService` only calls `NotifyAuthenticationStateChanged` from that event, so `<AuthorizeView>` and the cascading `Task<AuthenticationState>` keep a ClaimsPrincipal built from the stale permission set until a full page reload. - **[medium]** IAuthSource forces every consumer to implement a method the framework never calls
  
  `Source/Zonit.Extensions.Auth/Sources/IAuthSource.cs:30`

- **[medium]** UserModel.Policy holds permission tokens; DisplayRole is unrelated to Roles

- **[low]** AuthenticationSchemeService returns Fail() where IAuthSource's contract promises 'anonymous'

### Zonit.Extensions.Cultures

- **[medium]** Current.Value is canonically cased ("pl-PL") while every other tag in the system is lowercase â€” ordinal comparisons silently fail
  
  `Source/Zonit.Extensions.Cultures/Services/CultureStateService.cs:26,37-44`

   restore → build → pack → push, bez żadnego kroku instalującego wynik. Oba ship-blockery przeszłyby
   przez ten pipeline ponownie. `Example/Zonit.Extensions.ConsumerGate` łapie je lokalnie, ale realną
   ścieżką jest `PackageReference` do spakowanego `.nupkg` z lokalnego feedu — to inna ścieżka niż
   `ProjectReference` i to ona zawiodła dwa razy.
2. **Analizatory w repo nie widzą tego, co widzi ILC.** Solucja buduje się 0/0, a Native AOT publish
   raportuje ostrzeżenia w kodzie Zonit. Roslynowe analizatory trim/AOT są przybliżeniem; jedynym
   wiarygodnym sprawdzeniem jest `dotnet publish /p:PublishAot=true` z paczkami jako
   `TrimmerRootAssembly`.
3. **Brak `PackageValidation`.** `AssemblyVersion` jest celowo zamrożony na `10.0.0.0` w całej linii
   10.x, więc zmiana binarnie łamiąca nie daje niezgodności tożsamości assembly ani błędu ładowania —
   ujawnia się jako `MissingMethodException` w aplikacji konsumenta. `EnablePackageValidation` +
   `PackageValidationBaselineVersion` wykryłyby to przy `pack`. Nie włączone w preview.10, bo ten
   release celowo zawiera breaking changes; do włączenia od preview.11 z baseline `10.0.0-preview.10`.
